# 渠道游戏运营中心设计方案

> 产品名称：渠道游戏运营中心（Partner Game Console）  
> 项目代号：`partner`  
> 项目目录：`D:\workspace\website\www\rummy\partner`  
> 文档状态：需求与总体设计基线（待评审）  
> 最后更新：2026-11-19

## 1. 项目定位

为 `indiarummy_server` 的 API 游戏业务建设一个独立后台，服务对象是 `indiarummy_game.d_channel_parter` 表中的合作渠道商户。

该后台负责：

- 渠道商户及其接入配置管理；
- 渠道玩家、游戏记录和经营数据查询；
- 按商户、游戏、币种进行统计分析；
- 游戏配置、RTP 配置和库存控制；
- 配置发布、运行状态确认、版本历史和回滚；
- 安全控制、权限隔离和操作审计。

新项目与现有 `admin` 后台同级，保持独立部署和权限体系，但可参考现有 `admin` 的功能、数据口径与内部服务调用方式。

IndiaRummy 在本系统中是唯一游戏提供方，因此不设计“游戏厂商”顶部分组，也不引入无意义的 `provider_id`。经真实表结构与 `slotinventorymgr` 加载逻辑核准，控制策略与运行库存采用两个不同维度：

```text
控制策略：channel_id + game_id（同一渠道的所有币种共享）
运行库存：channel_id + game_id + currency_code（按币种隔离）
```

界面在发布控制预设时必须明确提示“将影响该渠道此游戏的全部币种”；币种筛选用于投注档位、库存和实际数据观察，不得让用户误以为策略可按币种分别发布。

## 2. 建设原则

1. 商户只能访问本渠道的数据，租户边界必须由服务端会话确定。
2. 涉及游戏运行状态的写操作不能只修改数据库，必须调用内部管理接口完成热加载并确认结果。
3. RTP、中奖率等指标必须展示真实定义，不允许用前端展示值掩盖实际配置。
4. 商户使用经过校准和授权的预设方案，不直接编辑底层权重或任意指定玩家输赢。
5. 所有敏感操作必须可审计、可追溯、可回滚。
6. 各币种数据默认分开统计，未经明确汇率换算不得直接合计。

## 3. 用户与权限

### 3.1 平台管理员

拥有全局管理权限：

- 查看全部商户、玩家、记录与统计；
- 创建和维护商户、账号、线路、币种、钱包模式；
- 创建、授权和发布 RTP 预设；
- 调整、重置和回滚游戏库存；
- 重新加载渠道配置、控制配置和游戏数据集；
- 设置维护状态；
- 查看全部操作审计和异常告警。

### 3.2 商户管理员

只能管理当前登录账号所属渠道：

- 查看本渠道玩家、记录和统计；
- 查看已授权游戏及运行状态；
- 从平台授权的控制预设中选择、预览和申请/发布配置；
- 查看本渠道配置历史和审计记录。

商户管理员不能编辑底层权重 JSON，不能绕过库存保护，也不能对单个玩家设置强制输赢。

### 3.3 商户观察员

只读访问本渠道的仪表盘、玩家、记录、统计和配置状态，不具有任何发布或变更权限。

### 3.4 权限模型

- 登录会话中固化 `channel_id` 和角色；
- 商户接口不得信任前端传入的 `channel_id`；
- 平台接口可以显式选择商户，但需要单独权限；
- 页面按钮权限和服务端接口权限必须同时校验；
- 记录详情、导出等子接口不得成为权限绕过入口。

## 5. 运营总览

### 5.1 核心指标卡

- 累计平台利润；
- 今日平台利润；
- 累计投注；
- 今日投注。

建议同时提供投注人数、游戏局数、实际 RTP 和异常告警数量。

### 5.2 趋势图

默认展示近 7 天柱状图，可切换：

- 投注金额；
- 派彩金额；
- 平台利润；
- 实际 RTP；
- 活跃玩家数。

### 5.3 指标口径

```text
平台利润 = 投注金额 - 派彩金额
玩家净输赢 = 派彩金额 - 投注金额
实际 RTP = 派彩金额 / 投注金额
```

无投注时 RTP 显示为 `--`，不得显示为 0%。多币种默认分别展示；如需折算为基准币种，必须展示汇率来源和换算时间。

## 8. 数据统计

支持按小时、日期、商户、游戏、币种聚合：

- 投注金额；
- 派彩金额；
- 平台利润；
- 实际 RTP；
- 目标 RTP/理论 RTP；
- 投注人数；
- 游戏局数；
- 派彩局命中率；
- 净赢局命中率；
- 50 倍、100 倍及以上次数；
- Bonus/免费游戏触发率；
- 最大单局派彩；
- 平均投注；
- 新老玩家拆分。

需要明确区分：

- 单次付费 SPIN RTP；
- 跨局收集奖励完整周期 RTP；
- 指定统计周期内的实际 RTP。

“中奖率”不使用单一含混指标，至少拆分为：

```text
派彩局命中率 = 派彩金额 > 0 的局数 / 总局数
净赢局命中率 = 派彩金额 > 投注金额的局数 / 总局数
```

## 10. 接入安全

后台登录前必须校验 IP 白名单。建议新增独立白名单表：

```text
d_channel_admin_ip_whitelist
```

建议字段：

```text
id
channel_id
ip_or_cidr
status
remark
created_by
create_time
update_time
```

应保留受严格审计的平台紧急恢复通道，避免错误配置导致所有管理员无法登录。

其他安全要求：

- 密码安全存储、登录失败限制和会话超时；
- 敏感操作二次确认；
- 配置发布使用幂等请求；
- 版本更新使用乐观锁，防止并发覆盖；
- 导出数据需要权限与审计；
- 日志记录操作者、来源 IP、前后值、版本、时间和结果。

## 12. RTP 与中奖率调控

### 12.1 现有基础

服务端现有能力可以按渠道、游戏、币种配置，核心数据与服务包括：

- `s_slot_control_profile`；
- `d_slot_inventory`；
- `d_slot_inventory_ledger`；
- `slotinventorymgr`。

### 12.2 商户可用方式

商户不编辑原始权重。平台为每款游戏离线跑数并校准若干预设，例如：

- 利润优先；
- 均衡；
- 体验优先；
- 大奖活动；
- 特定运营活动。

每个预设必须展示该游戏实测的 RTP、各类命中率、波动度、最大风险和样本量。平台按“商户 + 游戏”授权可用预设，并可单独授权目标 RTP、目标中奖率的最小值、最大值、步长，以及历史回滚和恢复平台默认能力。

商户可在授权范围内填写目标 RTP 和中奖率，但该输入不是直接修改底层权重。后台只在已授权、已校准的预设中选择最接近的可达方案，预览页同时展示“请求目标、实际可达值、偏差和采用方案”；商户确认后才发布。当前预设无法达到的目标不得伪装成已精确支持，如需增加新的可达点，仍需经过离线校准、金额与完整流程校验后新增预设。

### 12.3 发布流程

```text
选择授权预设，或输入授权范围内的目标值
  -> 目标值匹配最近的已校准可达方案，并明确展示偏差
  -> 预览该游戏的精确数据集和统计指标
  -> 校验金额、权重、完整流程及收集约束
  -> 生成不可变版本
  -> 写入数据库
  -> 调用 reloadChannel/对应内部加载接口
  -> 确认运行节点已加载该版本
  -> 监控实际数据，异常时回滚
```

渠道专属配置可以一键恢复为平台默认；恢复操作通过停用渠道覆盖版本实现，之后继续跟随平台默认配置更新。回滚和恢复默认都创建审计记录，不覆盖历史。

目标 RTP 是长期统计目标，短期实际 RTP 必然存在波动，界面必须同时展示样本量和统计周期。

库存保护、赔付预算和潜在负债预留属于平台安全边界，商户无权关闭。

### 12.4 首批支持范围

现代 `cashslots` 控制体系可优先覆盖：

```text
419, 541, 635, 692, 693, 695, 696, 698, 699
```

其他游戏需要逐款增加适配器，不应把旧游戏的 `killrate` 语义强行伪装成统一 RTP 控制。

### 12.5 收集类游戏约束

收集类游戏的控制配置、数据集生成和校验必须遵守项目根目录 `AGENTS.md`：

- 增加收集进度的付费 SPIN 必须是真实 0 倍结果；
- 含收集图标且有赔付的样本不进入进度池；
- 数量档位按准确图标数量区分并独立使用正整数权重；
- 收集档位与普通 SPIN 在同一 10000 权重组中计算；
- 默认总出现概率不超过 35%；
- 重分配权重后重新校准 RTP，并区分单次 SPIN 与跨局奖励。

## 13. 玩家调控设计

参考后台中的“点控、养成、收割”界面具有一些可借鉴的交互：

- 当前、已完成、已进入数量卡片；
- 生效时间与到期时间；
- 目标值与实际值对比；
- 数据、记录、导出、取消；
- 自动到期和冲突提示。

根据后续确认，玩家调控扩展为正式能力，支持：

- `SUPPORT`：在库存和完整玩法允许范围内优先选择达到最低派彩区间的结果；
- `SUPPRESS`：压低结果派彩上限，累计玩家净亏达到目标后结束；
- `RTP_TARGET`：根据任务周期内累计投注与派彩，动态向目标 RTP 收敛；
- 目标金额、最大局数、生效/到期时间、优先级和操作原因；
- 当前、完成、取消、到期统计，以及逐局不可变执行流水；
- 相同玩家、游戏、币种只允许一个活动任务；达到任一停止条件自动完成；
- 任务始终受真实库存、潜在负债、最大赔付、数据集可达结果及完整玩法约束。

运行端使用独立 `d_slot_player_control` 与 `d_slot_player_control_event`，不恢复旧的 `reloadUser` 实现；后台通过新的签名 `reloadplayercontrol` 动作加载，任务进度与游戏结算在同一数据库事务中推进。

## 14. 技术架构

```text
浏览器
  -> partner 独立后台应用
       -> MySQL（查询、报表、配置版本、审计）
       -> 内部管理 API
            -> Skynet 服务
                 - channelpartermgr
                 - slotinventorymgr
                 - gamemgr
```

### 14.1 数据读写原则

- 玩家、记录和统计可从数据库及聚合表读取；
- 会影响在线游戏运行的配置必须通过内部管理 API 发布；
- 发布成功的判断标准不是数据库写入成功，而是目标运行节点确认已加载指定版本；
- 聚合报表应避免按商户逐条查询导致 N+1；
- 跨月游戏记录需要统一游标/分页策略，避免分页重复或遗漏。

## 17. 验收标准

1. 商户账号无法通过任何接口访问其他 `channel_id` 的数据。
2. 不同币种默认独立展示和计算。
3. 游戏记录包含稳定的商户归属、币种、局号和控制版本快照。
4. 控制预设发布前完成金额、权重、流程和游戏特殊规则校验。
5. 发布后能确认运行节点已加载指定版本。
6. 配置支持完整版本历史和一键回滚。
7. 实际 RTP、目标 RTP、命中率口径和样本量清晰可核对。
8. 商户不能编辑底层权重、关闭库存保护或设置玩家强制输赢。
9. 登录、密钥、白名单、配置、回滚和导出全部有审计记录。
10. 关键统计和游戏记录查询满足约定的性能指标。
